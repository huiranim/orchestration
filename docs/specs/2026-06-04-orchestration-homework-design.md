# 데이터 플랫폼 오케스트레이션 설계 및 구현

> Airflow vs Dagster 비교 분석을 통한 우선순위·동시성·의존성 제어 실습

---

## 1. 과제 목적 및 습득 역량

이 과제는 단순히 오케스트레이션 툴 사용법을 익히는 것이 아니라, **실제 운영 환경에서 발생하는 파이프라인 제어 문제를 스스로 설계하고 해결하는 역량**을 기른다.

### 1-1. 오케스트레이션 개념 역량
- DAG, Task, Executor, Scheduler 등 핵심 개념을 이해하고 직접 설계에 적용할 수 있다
- 스케줄링, 의존성, 재시도, 동시성 제어가 실제로 어떻게 동작하는지 구현을 통해 체득한다

### 1-2. 도구 평가 역량
- 동일한 문제를 Airflow와 Dagster로 각각 풀어보고, 아키텍처·개발 경험·운영 적합성 차이를 직접 체감한다
- 주어진 기술 환경과 요건에 맞는 도구를 선택할 수 있는 판단 기준을 갖는다

### 1-3. 운영 문제 해결 역량
- 우선순위 선점, 동시성 충돌, 의존성 전파, 선택적 재실행 등 실무에서 자주 마주치는 오케스트레이션 문제를 직접 구현하고 검증한다

### 1-4. 현행 시스템 분석 및 개선 역량
- 학습한 내용을 바탕으로 `didimdp_manager`의 구조적 한계를 재해석하고, 개선 방향을 구체적으로 도출한다

## 2. 배경: didimdp_manager 한계

현재 회사는 자체 개발한 DAG 기반 파이프라인 오케스트레이터 `didimdp_manager`를 운영 중이다. 구조적 한계 중 이 과제에서 집중적으로 다루는 항목은 다음과 같다.

| 한계 항목 | 현상 |
|---|---|
| 우선순위 처리 부재 | 대기열이 FIFO 고정. 긴급 작업이 낮은 우선순위 작업보다 먼저 실행되지 않음 |
| 동시성 제어 불안정 | 로컬 카운터 기반 슬롯 관리로 실제 Spark 자원과 괴리 발생 가능 |
| 선택적 재실행 미지원 | 특정 태스크만 재실행하는 기능 없음. 실패 시 전체 재실행 필요 |
| 크로스 DAG 의존성 제한 | 선행 DAG 전체 성공만 인정. 조건부 의존성 불가 |

## 3. Airflow vs Dagster 비교

### 3-1. 아키텍처 및 핵심 패러다임

| 항목 | Airflow | Dagster |
|---|---|---|
| 핵심 추상화 | DAG + Task | Asset + Op |
| 실행 단위 | Task (실행할 작업) | Op(실행 단위) + Asset(실행 결과물: 테이블·파일·모델 등) |
| 의존성 표현 | Task 간 실행 순서 제약 | 데이터 자산 간 계보(lineage) |
| 스케줄 단위 | DAG Run | Asset Materialization |
| 주요 컴포넌트 | Webserver, Scheduler, Executor, MetaDB | Webserver(Dagit), Daemon, Run Launcher, Code Server |

두 도구 모두 작업의 순서와 실행 시점을 제어하는 것이 목적이지만, 출발점이 다르다.

Airflow는 **실행할 작업**을 중심에 놓는다. "주문을 수집하고, 정규화하고, 적재한다"는 절차를 DAG로 선언하면 스케줄러가 그 절차를 순서대로 실행한다. 운영자는 파이프라인이 제대로 돌았는지를 기준으로 시스템을 바라본다. 실행 순서와 스케줄이 고정된 배치 파이프라인, 특히 Spark·Hive 같은 데이터 엔지니어링 스택과의 조합에 적합하다.

Dagster는 **만들어야 할 데이터**를 중심에 놓는다. "`orders_normalized` 테이블을 만들려면 `orders_raw`가 먼저 있어야 한다"는 자산 간 관계를 선언하면 실행 순서는 Dagster가 추론한다. 운영자는 데이터가 최신 상태인지를 기준으로 시스템을 바라본다. 여러 팀이 데이터 자산을 공유하거나 테이블 간 계보를 추적해야 하는 환경에 적합하다.

이 과제처럼 처리 흐름이 고정된 Spark 배치 파이프라인에서는 두 방식의 최종 실행 결과가 같다. 의존성을 표현하는 방식, 재실행 단위, 운영 중 시스템을 바라보는 관점의 차이를 직접 구현하며 체감한다.

### 3-2. 이 과제의 핵심 기능별 비교

| 기능 | Airflow | Dagster |
|---|---|---|
| **우선순위 제어** | `priority_weight` 설정 + Pool 큐에서 높은 값 우선 소비 | `priority` 설정 + Concurrency limit 기반 조율 |
| **동시성/슬롯 제어** | Pool (슬롯 수 명시적 설정). 슬롯 초과 시 대기열 진입 | Concurrency limit (동시 실행 Op/Run 수 제한). 초과 시 대기 |
| **크로스 DAG 의존성** | ExternalTaskSensor로 다른 DAG 완료 대기 | Asset 간 의존성으로 자연스럽게 표현 |
| **선택적 태스크 재실행** | UI에서 특정 Task만 Clear & Re-run | Asset 단위 재 materialization 선택 |
| **Spark 연동** | `SparkSubmitOperator` 공식 지원 | `@op` 내 PySpark 직접 호출 또는 subprocess |
| **스케줄링** | cron 표현식, 외부 트리거(API) | cron 표현식, 센서 기반 이벤트 트리거 |

### 3-3. 운영 및 학습 관점 비교

| 항목 | Airflow | Dagster |
|---|---|---|
| 운영 성숙도 | 매우 높음 (2015~, 가장 넓은 채택) | 높음 (2019~, 빠르게 성장 중) |
| 로컬 셋업 | Docker Compose 필요 (Postgres, Redis, Worker) | `dagster dev` 한 줄로 실행 |
| UI | DAG 시각화, 실행 이력, 태스크 단위 로그 | Asset 계보 시각화, Run 상세, 센서 상태 |
| didimdp_manager와의 패러다임 거리 | 가까움 (DAG + Task 기반으로 유사) | 멀음 (Asset 기반으로 전환 비용 존재) |
| 레퍼런스/커뮤니티 | 압도적으로 풍부 | 충분하지만 상대적으로 적음 |
| 학습 곡선 | 낮음 (기존 DAG 개념 연장선) | 중간 (Asset 패러다임 전환 필요) |

### 3-4. 도구 선택 기준

2주차 미니 파이프라인 비교 구현 후 아래 기준으로 최종 선택한다:

1. **우선순위 + 동시성 제어**가 직관적으로 표현되는가?
2. **크로스 파이프라인 의존성** 설정이 명확한가?
3. **선택적 재실행** UI/API가 사용하기 편한가?
4. **Spark 연동** 설정 난이도가 적절한가?
5. 학습 후 **didimdp_manager 개선 제안**에 활용 가능한 인사이트가 풍부한가?

## 4. 비즈니스 시나리오

### 4-1. 환경 가정

- **Spark 실행 슬롯**: 최대 3개 (개발 서버 리소스 제약 — 각 Spark Job 약 5 core 점유 기준)
- **Spark 환경**: Local 모드 (`spark.master=local[*]`)
  - **선택 근거**: Spark 실행 환경 선택지는 Local, Standalone, YARN, Kubernetes, 매니지드 서비스(EMR·Databricks 등)이다. 운영환경에서는 YARN·Kubernetes·매니지드 서비스를 사용한다. 이 과제는 오케스트레이션 학습이 목적이므로 클러스터 구성 없이 바로 시작할 수 있는 Local 모드를 선택한다. 단일 JVM 내 멀티스레드 방식으로 실제 분산 처리는 아니나, 오케스트레이터가 Job을 제출하고 완료를 감지하는 흐름은 동일하게 경험할 수 있다.
- **구현 언어**: Python (PySpark)
  - Airflow/Dagster DAG 코드와 언어 통일
  - 시장에서 Spark와 가장 흔히 연동되는 언어
- **Spark 태스크 구현 방식**: 모두 스텁으로 구현
  - 실제 비즈니스 로직 없이 `time.sleep` + 성공/실패 시뮬레이션으로 대체
  - 오케스트레이션 동작(순서, 의존성, 자원 경합, 재시도) 검증에 집중
  - 실제 SparkSession을 생성하고 실행하는 형태 유지 — 오케스트레이터가 Spark Job을 실제로 제어하는 경험 보존

```python
# 스텁 예시
def spark_task_stub(task_name: str, duration_sec: int = 10, fail: bool = False):
    spark = SparkSession.builder.appName(task_name).master("local[*]").getOrCreate()
    time.sleep(duration_sec)  # 처리 시간 시뮬레이션
    if fail:
        raise Exception(f"{task_name} intentionally failed")
    spark.stop()
```

- **Spark 실행 슬롯 설계 근거**
  - 슬롯 3개: P1(1) + P3(1) + 여분(1)으로 정상 운영 가능한 최소 수. 여분이 있어야 긴급 실행이 즉시 가능
  - P4 슬롯 2개: 모델 학습의 리소스 집약성을 표현. P4 실행 중 P3 긴급 트리거 시 슬롯 1개만 남아 "우선순위 선점이 필요한" 상황을 의도적으로 연출
  - 슬롯은 오케스트레이터의 Pool 설정으로 제어하는 논리적 제약이며, 실제 Spark 자원 사용량과 1:1 대응하지 않음

### 4-3. 오케스트레이션 시나리오

#### 시나리오 A — 우선순위 선점

> 월요일 새벽 2시, P4 T3(모델 학습, 슬롯 2개)가 실행 중. 운영팀이 P3 긴급 트리거.
> P3(슬롯 1개)는 남은 슬롯 1개로 즉시 시작.
> P4가 추가 슬롯 요청 시 P3가 우선 확보하는지 검증.

**검증 포인트**: 우선순위 높은 P3가 낮은 P4보다 슬롯을 먼저 확보하는가?

#### 시나리오 B — 동시성 제어

> 자정에 P1(슬롯 1)과 P3(슬롯 1)가 동시에 시작. P2는 P1 완료 후 슬롯 1개 추가 요청.
> 월요일 자정이라면 P4(슬롯 2)도 동시 경합 → 총 요청 슬롯 5개 > 한계 3개.
> P4는 우선순위 최하위이므로 대기열 진입. 슬롯 반납 시 우선순위 순서로 소비되는지 검증.

**검증 포인트**: 슬롯 초과 시 대기열이 우선순위 순서로 소비되는가?

#### 시나리오 C — 의존성 + 선택적 재실행

> P1의 T3(DW 적재) 실패 → P2·P3 실행 차단.
> T3만 수동 재실행 → 성공 시 P2·P3 자동 재개.

**검증 포인트**: T1·T2 재실행 없이 T3만 재실행되는가? P2·P3가 자동 unblock되는가?
