# 2주차 비교 분석 — Airflow vs Dagster 미니 파이프라인 구현

> 동일한 P1 주문 수집 파이프라인(T1→T2→T3)을 두 도구로 구현하고,
> 추가로 우선순위/동시성·크로스 파이프라인 우선순위 미니 실험까지 수행해 비교한다.
> 구현 범위: 기본 의존성 + SparkSession stub + 선택적 재실행 + 우선순위/동시성(축소판).
> 구현일: 2026-06-13 ~ 06-14

---

## 1. 직접 구현으로 검증한 항목

### 1-1. 셋업 난이도

| 항목 | Airflow | Dagster |
|---|---|---|
| 핵심 명령 | `airflow standalone` | `dagster dev -f definitions.py` |
| 컴포넌트 | webserver + scheduler + triggerer + gunicorn(워커 4) | webserver + daemon + code server |
| 의존성 설치 | 공식 constraints 파일 필수 (충돌 방지) | `pip install -r` 한 줄, constraints 불필요 |
| 설정 항목 | `AIRFLOW_HOME`, `DAGS_FOLDER`, `DAG_DIR_LIST_INTERVAL`, `LOAD_EXAMPLES` 등 다수 | 거의 없음 (진입점만 지정) |
| 막힌 지점 | **다수** (아래) | 경미 (아래) |

**Airflow에서 막힌 지점** (실제 트러블슈팅):
1. **macOS gunicorn 워커 SIGSEGV** — fork 후 `setproctitle`이 fork-safe하지 않은 CoreFoundation 호출. no-op 셰임으로 우회. (가장 큰 블로커, [[2026-06-13-환경구성]] 참고)
2. **Python 3.9 LibreSSL 문제** — 시스템 Python 3.9는 LibreSSL이라 충돌. Homebrew Python 3.11로 재구성.
3. **예제 DAG 69개 자동 로드** — `LOAD_EXAMPLES=False` + `db reset` 필요.
4. **신규 DAG 감지 지연** — `DAG_DIR_LIST_INTERVAL` 기본 5분 → 10초로 단축.

**Dagster에서 막힌 지점**:
1. **`dagster dev` 인자 없이는 실패** — `[tool.dagster]` 블록이나 `-f` 필요. `-f definitions.py`로 해결.
2. **`dagster dev` deprecated 경고** — 최신 버전은 `dg dev` 권장 (별도 패키지). 동작에는 지장 없음.
3. macOS 고유 문제 없음. (Dagster는 uvicorn 단일 프로세스라 gunicorn fork 이슈 없음)

> **체감 결론**: 셋업은 Dagster가 압도적으로 가벼웠다. Airflow는 환경 트러블슈팅에 상당한 시간을 썼다. 단, 이는 macOS 로컬 + standalone 조합 특성이며, 운영환경(Docker/Linux)에서는 양상이 다를 수 있다.

### 1-2. 코드 작성 방식

| 항목 | Airflow | Dagster |
|---|---|---|
| 파이프라인 정의 | `with DAG(...) as dag:` 컨텍스트 | `@asset` 데코레이터 함수 |
| 실행 단위 | `PythonOperator(task_id, python_callable, op_kwargs)` | `@asset` 함수 본문 |
| 의존성 선언 | `t1 >> t2 >> t3` (실행 순서) | `deps=[orders_raw]` (데이터 계보) |
| 진입점 | `dags/` 폴더 자동 스캔 | `Definitions(assets=[...])` 명시 |
| 공유 로직 | 양쪽 모두 동일한 `shared/stubs.py`의 `spark_task_stub` 호출 | (동일) |

**체감** (직접 구현 기준):
- 간단한 예제(P1 3개 태스크)에서는 **두 방식의 난이도가 비슷**했다.
- Airflow는 "여러 task를 DAG로 묶고 task 간 순서를 정의한다"는 흐름.
- Dagster는 "독립적인 asset 함수 여러 개를 정의해두면 `deps`에 의해 순서와 lineage가 정해지고 그대로 실행된다"는 흐름.
- **단, 작업이 복잡해졌을 때의 차이는 아직 와닿지 않음.** (간단한 예제의 한계 — Week 3~4 전체 시나리오에서 재확인 필요)

### 1-3. Spark 연동

`local[*]` 모드에서는 두 도구 모두 함수 내에서 `SparkSession.builder...local[*]`로 동일하게 처리. 연동 난이도 차이 없음.

### 1-4. 선택적 재실행 (시나리오 C 메커니즘)

| | Airflow | Dagster |
|---|---|---|
| 방법 | 태스크 클릭 → **Clear & Re-run** | 자산 선택 → **Re-materialize** |
| 검증 결과 | `load_to_dw`만 재실행, 상류 태스크 미실행 ✓ | `orders_dw`만 재실행, 상류 자산 미실행 ✓ |
| 코드 변경 반영 | 스케줄러 자동 재스캔 (폴링 10초) | watchfiles 자동 감지 (저장 즉시) |

**체감**: UI 조작은 **둘 다 비슷하게 간단**했다. 둘 다 didimdp_manager가 못 하는 "특정 단위만 재실행"을 쉽게 달성.

> **미검증 영역**: 이번엔 **UI 조작**만 확인. 솔루션 내부에 도입하려면 **코드/API 제어** 수준을 봐야 하는데 아직 미검증. → Week 6~7 재검토.

### 1-5. 단일 파이프라인 내 우선순위/동시성 (시나리오 A/B 축소판)

슬롯 1개로 제한하고, 의존성 없는 3개 작업(high/mid/low)을 동시에 제출 → 우선순위 순으로 소비되는지 검증.

| | Airflow (`priority_demo`) | Dagster (`priority_demo_job`) |
|---|---|---|
| 동시성 제한 | `airflow pools set spark_pool 1` (CLI 한 줄) | `DAGSTER_HOME` + `dagster.yaml`(`pools.default_limit:1`) |
| 우선순위 지정 | `priority_weight=10` (operator 인자) | `tags={"dagster/priority":"10"}` (op 태그) |
| 실행 모델 | Task/DAG → Trigger | Op/Job → Launch Run (Asset은 Materialize) |
| 결과 | **high→mid→low 순 실행 ✓** | **high→mid→low 순 실행 ✓** |

**체감**: **한 파이프라인 내부**에서는 둘 다 우선순위 정렬이 잘 작동. 단 Dagster는 동시성 설정에 인스턴스 설정 파일(`dagster.yaml`)이 필요해 Airflow의 CLI 한 줄보다 손이 더 갔다.

### 1-6. 크로스 파이프라인 우선순위 (시나리오 A 핵심) — **결정적 차이**

슬롯 1개를 공유하는 파이프라인 2개(A: 낮음, B: 높음). A 실행 중에 B를 트리거 → 슬롯이 빌 때 누가 먼저인지 검증.

| | Airflow (`cross_dag_priority`) | Dagster (`cross_job_priority`) |
|---|---|---|
| 우선순위 작동 단위 | **태스크 레벨** (Pool + `priority_weight`) | op 풀은 동시성만, 우선순위는 **run 레벨** 별도 |
| 관측 결과 | b 완료 후 **c(A)보다 d(B) 먼저** → B 체인 전부 후 A 나머지 ✓ | run_b가 **통째로 대기**, A 완료 후에야 B 실행 ✗ |
| 선점(preemption) | 없음 (실행 중 작업은 안 멈춤) | 없음 |

**공식 문서로 확인한 원인** (Dagster 1.13.9):
- op 동시성 풀은 "동시 실행 op 개수"만 전역 제한. **슬롯 배분에 op 우선순위를 쓰지 않음.**
- op `dagster/priority`는 **"only applied on a per-run basis"** — 한 run 내부 정렬 전용. run을 넘나들지 못함.
- 크로스 파이프라인 우선순위의 의도된 방법 = **run 태그 `dagster/priority` + QueuedRunCoordinator.** 단 이는 "대기 중인 run 중 어느 걸 먼저 **시작**할지"만 결정하고, **선점·op 단위 끼어들기 없음.**
- **op 단위 크로스 run 우선순위는 OSS 기본 구성으로 불가능. Celery executor(별도 인프라) 필요.**

> **핵심 결론**: 시나리오 A/B가 요구하는 "슬롯 공유 + 크로스 파이프라인 **op/태스크 레벨** 우선순위"를 **Airflow는 경량 LocalExecutor + Pool만으로 기본 충족**한다. **Dagster는 기본 구성(멀티프로세스 executor)으로는 불가능**하고, op 단위 크로스 run 우선순위를 얻으려면 **Celery executor**가 필요하다(§1-7). 단, Dagster도 **run 레벨 우선순위**(QueuedRunCoordinator)는 추가 인프라 없이 가능하므로, "굵은 단위(어느 파이프라인을 먼저 시작)"로 타협하면 로컬에서도 일부 표현은 된다.

**운영 주의(문서 발견)**: Dagster 풀은 run 취소/실패 시 슬롯이 자동 반환되지 않아 `default_limit:1`에서 deadlock 가능 → `run_monitoring.free_slots_after_run_end_seconds` 설정으로 방지(우리 `dagster.yaml`에 반영).

### 1-7. 보충: Celery란? 왜 Dagster op 우선순위에 필요한가

**Celery** = 파이썬 **분산 작업 큐**. 작업을 **메시지 브로커**(Redis 또는 RabbitMQ)에 쌓아두고, 여러 **worker 프로세스**가 꺼내서 실행한다. 여러 프로세스/머신으로 확장 가능.

| 구성요소 | 역할 |
|---|---|
| 브로커 (Redis/RabbitMQ) | 작업 대기열 저장·전달 |
| worker(s) | 대기열에서 작업을 꺼내 실행 |
| (result backend) | 실행 결과 저장 (선택) |

- **Airflow의 CeleryExecutor**: 태스크를 Celery로 여러 worker에 분산. (※ 이 과제 명세서가 원래 상정한 "Postgres + Redis + Worker" 구성이 바로 이것)
- **Dagster의 celery_executor**: op 실행을 Celery로 분산하면서, **여러 run에 걸친 op 우선순위·큐잉 control plane**을 제공 → §1-6에서 막혔던 "op 단위 크로스 run 우선순위"가 가능해진다.
- **비용**: 브로커(예: 로컬 Redis 컨테이너) + worker 프로세스를 추가로 띄워야 함. 로컬 `dagster dev` 단독보다 무겁다. (단 로컬에서 Redis 하나 띄우면 구성 자체는 가능)

**중요한 비대칭 (선택 판단의 핵심)**:
- 과제의 "Local 모드"는 **Spark 실행 모드**(`spark.master=local[*]`) 제약이지, **오케스트레이터 인프라** 제약과는 별개다. 즉 Celery를 쓰는 것 자체가 과제 위반은 아니다(명세서도 Airflow에 Redis+Worker를 상정).
- 그러나 **Airflow는 Celery 없이(LocalExecutor)도 태스크 레벨 우선순위가 되는 반면, Dagster는 op 레벨 우선순위를 위해 Celery가 필요**하다 — 같은 목표를 위한 **인프라 부담이 다르다**는 점이 핵심.

## 3. 도구 선택

**현재 판단: 보류 — 두 도구를 모두 열어둔다.** 결정에 필요한 핵심 변수(시나리오 A/B를 어느 충실도로 구현할지, Celery 도입을 감수할지)가 아직 확정되지 않았다.

### 3-1. 지금까지 드러난 트레이드오프

| 기준 | Airflow | Dagster |
|---|---|---|
| 셋업 경량성 | 무거움 (트러블슈팅 다수) | **가벼움** |
| 코드 직관성 (간단 예제) | 대등 | 대등 |
| 선택적 재실행(UI) | 대등 | 대등 |
| 단일 파이프라인 우선순위 | 가능 | 가능 |
| **크로스 파이프라인 우선순위 (시나리오 A/B 핵심)** | **경량 구성으로 기본 충족** | 기본 불가, Celery 필요 (또는 run 레벨로 타협) |
| didimdp_manager 매핑 | **가까움** (Task 기반) | 멂 (Asset/Run 기반, 참고 가치는 있음) |
| 패러다임 학습 가치 | 낮음 (기존 연장선) | **높음** (자산 중심 신규) |

### 3-2. 양측 입장 정리

- **Airflow로 기운다면**: 시나리오 A/B를 추가 인프라 없이 태스크 레벨로 충실히 구현 가능하고, didimdp_manager 개선 제안에 직접 매핑된다. 과제 완수 리스크가 가장 낮다.
- **Dagster로 기운다면**: 자산 패러다임을 깊이 학습하는 가치가 크다. 단 시나리오 A/B는 ①run 레벨 우선순위 + 여분 슬롯으로 "축소 구현"하거나 ②로컬 Redis로 Celery executor를 띄워 op 레벨까지 충실히 구현하는 두 갈래 중 선택해야 하며, 어느 쪽이든 범위·난이도가 늘어난다.

### 3-3. 결정을 내리기 위해 더 필요한 것 (3주차 초반에 판단)

3주차 첫 작업으로 아래를 짧게 확인한 뒤 최종 결정한다:
1. 시나리오 A/B를 **어느 충실도**로 요구할지 확정 — "긴급 파이프라인이 먼저 시작"(run 레벨)으로 충분한가, 아니면 "진행 중 파이프라인 사이를 op 단위로 파고들기"(태스크/op 레벨)까지 필요한가.
2. Dagster 선택 시 **Celery 도입 의향** 여부 (로컬 Redis 추가 감수 가능한지).
3. 위 결과에 따라 도구 확정 후 P1~P4 전체 시나리오 구현 시작.

## 4. didimdp_manager 개선 관점 시사점 (8주차 제안서용 메모)

이번 비교에서 도출한, 현행 시스템 개선에 직접 연결되는 발견:

1. **우선순위는 "선점"이 아니라 "대기열 정렬"이다.** Airflow·Dagster 둘 다 실행 중 작업을 멈추지 않는다. 긴급성은 **여분 슬롯**으로 보장한다(명세서 3슬롯 = P1+P3+여분 설계의 근거). → didimdp_manager에 선점을 넣기보다 **우선순위 큐 + 여분 슬롯** 조합이 현실적.
2. **우선순위를 어느 레벨에 두느냐가 핵심 설계 갈림길.** 태스크 레벨(Airflow) = 세밀한 크로스 파이프라인 제어, run 레벨(Dagster 기본) = 굵은 제어. didimdp_manager의 FIFO를 개선하려면 **태스크 레벨 우선순위 큐**가 목표가 되어야 하며, Airflow Pool+priority_weight가 직접 참고 모델.
3. **동시성 풀의 슬롯 누수 주의.** 작업 실패/취소 시 슬롯 자동 반환이 없으면 deadlock 위험 → 자동 반환 타임아웃 메커니즘 필요.
