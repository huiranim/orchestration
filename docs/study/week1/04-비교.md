# 블록 4 — Airflow vs Dagster 개념 비교

> 과제 명세서 §3-4의 5대 선택 기준을 개념 수준에서 정리한다.
> 실제 선택은 2주차 미니 파이프라인 구현 후 체감 기반으로 결정한다.

---

## 4.1 패러다임 대비

| | Airflow | Dagster |
|---|---|---|
| 핵심 질문 | 무엇을 **실행**할까? | 무엇을 **만들** 것인가? |
| 기본 단위 | Task (실행 행위) | Asset (데이터 결과물) |
| 의존성 선언 | Task 간 실행 순서 (`>>`) | 데이터 자산 간 계보 (`deps=[]`) |
| 운영 관점 | "파이프라인이 제대로 돌았는가" | "데이터가 최신 상태인가" |
| UI 핵심 화면 | DAG 실행 그래프 | Asset Catalog (계보 시각화) |

```
Airflow:  T1(collect) ──→ T2(normalize) ──→ T3(load_to_dw)
          "이 행위들을 이 순서로 실행해라"

Dagster:  orders_raw ──→ orders_normalized ──→ orders_dw
          "orders_dw는 orders_normalized로부터 만들어진다"
```

---

## 4.2 아키텍처 컴포넌트 대응

| 역할 | Airflow | Dagster |
|---|---|---|
| 스케줄·트리거 판단 | Scheduler | Daemon |
| 실행 방식 결정 | Executor | Run Launcher (어디서) + Executor (어떻게) |
| 실제 코드 실행 | Worker | Worker (Executor가 띄움) |
| UI | Webserver | Webserver / Dagit |
| 상태 저장 | Metadata DB (Postgres) | Metadata DB (SQLite 가능) |
| 코드 위치 | DAG Directory (파일) | Code Location (파이썬 서버) |
| 로컬 실행 | Docker Compose 필요 | `dg dev` 한 줄 |

Dagster는 Executor를 Run Launcher와 두 레이어로 분리해 "어디서"와 "어떻게"를 독립적으로 제어한다. Airflow는 Executor 종류 선택이 "어디서 + 어떻게"를 함께 결정한다.

---

## 4.3 과제 5대 선택 기준별 비교

> 개념 수준 사전 정리. 2주차 구현 후 체감 기반으로 업데이트 예정.

### ① 우선순위 + 동시성 제어

| | Airflow | Dagster |
|---|---|---|
| 동시성 제한 단위 | Pool (슬롯 수 명시) | Concurrency Key (태그 + pool slots) |
| 우선순위 설정 | Task 단위 `priority_weight` | Job/Run 단위 `priority` |
| 슬롯 초과 시 | `queued` 상태 대기 → 우선순위 정렬 | Concurrency Key 대기열 → 우선순위 정렬 |

### ② 크로스 파이프라인 의존성

| | Airflow | Dagster |
|---|---|---|
| 구현 방법 | `ExternalTaskSensor` (DAG ID + Task ID 직접 참조) | `@asset_sensor` (Asset key만 참조) |
| 결합도 | **강결합** — 상류 DAG 구조 변경 시 Sensor 수정 필요 | **약결합** — 상류 파이프라인 구조와 무관 |
| 표현 방식 | "P1의 load_to_dw Task가 완료됐는가" | "orders_dw Asset이 생성됐는가" |

### ③ 선택적 재실행

| | Airflow | Dagster |
|---|---|---|
| 방법 | UI에서 Task 선택 → Clear & Re-run | UI에서 Asset 선택 → Re-materialize |
| 시나리오 C 적용 | T3 Task만 Clear → Re-run | orders_dw Asset만 re-materialize |

### ④ Spark 연동

| | Airflow | Dagster |
|---|---|---|
| 공식 방법 | `SparkSubmitOperator` (공식 Provider 제공) | `@op`/`@asset` 내 PySpark 직접 호출 |
| 과제 환경 (local mode) | `PythonOperator` + SparkSession 직접 생성 가능 | `@op/@asset` 내 SparkSession 직접 생성 |

과제는 `local[*]` 모드라 두 도구 모두 `SparkSession.builder.master("local[*]")`로 동일하게 처리 가능하다.

### ⑤ didimdp_manager 개선 인사이트

| | Airflow | Dagster |
|---|---|---|
| 우선순위 개선 힌트 | Pool + `priority_weight` — 논리 슬롯 + 우선순위 큐 구현 패턴 | Concurrency Key — 태그 기반 전역 동시성 제어 패턴 |
| 크로스 의존성 힌트 | ExternalTaskSensor — 명시적 폴링 방식 | AssetSensor — 데이터 결과물 기반 약결합 패턴 |
| 선택적 재실행 힌트 | Task Clear API — Task 단위 상태 초기화 메커니즘 | Re-materialize — 데이터 자산 단위 재실행 |

`didimdp_manager`와 Airflow는 모두 **Task 기반 구조**라 패러다임이 유사하다. 따라서 Airflow의 구현 패턴이 개선 제안에 더 직접 적용 가능한 힌트를 줄 가능성이 높다. Dagster의 약결합 의존성 설계는 구조적 개선 아이디어로 참고할 수 있다.

## 4.4 3대 시나리오 구현 방식 대비

| 시나리오 | Airflow | Dagster |
|---|---|---|
| **A (우선순위 선점)** | `spark_pool` + `priority_weight` | Concurrency Key pool + `priority` |
| **B (동시성 제어)** | Pool `slots=3` + 대기열 우선순위 정렬 | Concurrency Key `slots=3` |
| **C (의존성 + 재실행)** | `ExternalTaskSensor` + Task Clear & Re-run | `@asset_sensor` + Asset re-materialize |

---

## 4.5 운영·학습 환경 비교

| 항목 | Airflow | Dagster |
|---|---|---|
| 로컬 셋업 | Docker Compose (Postgres + Redis + Worker) | `dg dev` 한 줄 |
| 학습 곡선 | 낮음 — DAG·Task 개념이 직관적 | 중간 — Asset 패러다임 전환 필요 |
| 레퍼런스 | 압도적으로 풍부 (2015~) | 충분하지만 상대적으로 적음 (2019~) |
| didimdp_manager와 패러다임 거리 | 가까움 (DAG + Task 기반 유사) | 멀음 (Asset 기반, 전환 비용 존재) |
