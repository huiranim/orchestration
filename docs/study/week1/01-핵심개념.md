# 본문 (필수)

## 1.1 오케스트레이션은 왜 필요한가?

### 출발점: 스크립트 + cron

P1(주문 수집) `T1 주문 수집 → T2 정규화 → T3 DW 적재`를 파이썬 스크립트 + cron으로 짜면 작동은 하지만, **운영에 들어가면** 답할 수 없는 문제들이 생긴다.

### 스크립트 + cron이 깨지는 4가지 지점

| 문제 | 상황 (P1 기준) | `didimdp_manager` 연결 |
|---|---|---|
| ① 실패 처리 | T3만 죽어도 T3만 다시 못 돌림 → 전체 재실행 | "선택적 재실행 미지원" |
| ② 의존성 | P2는 P1 전체 성공 후 실행돼야 하는데 cron은 P1 결과를 모름 → 빈 데이터 위 집계 | "크로스 DAG 의존성 제한" |
| ③ 자원 경합 | 자정에 P1·P3·P4 겹치면 Spark 슬롯 요청 > 한계(3) → cron은 남은 슬롯을 모르고 다 실행 | "동시성 제어 불안정" |
| ④ 가시성 | 어젯밤 P3가 어느 단계에서 실패했는지 로그 말고는 알 수 없음 | (운영 추적 부재) |

### 오케스트레이터의 정의

> **여러 작업을, 올바른 순서로, 적절한 시점에, 자원 한도 안에서, 실패까지 관리하며 실행하고 그 상태를 추적하는 시스템.**

`didimdp_manager`·Airflow·Dagster 모두 이 문제를 푸는 도구. 이 과제는 "그 문제들을 더 잘 푸는 방법"을 배우는 것.

## 1.2 DAG와 Task

### Task (작업)
파이프라인을 이루는 **하나의 실행 단위**. 통째로 실행되고 성공/실패가 하나로 판정된다. (예: P1의 T1, T2, T3)

### DAG (Directed Acyclic Graph, 방향성 비순환 그래프)
Task들과 그 사이의 **의존 관계**를 표현한 그래프.

- **Directed (방향성)**: `T1 → T2` = "T1이 끝나야 T2 시작". 방향이 있다.
- **Acyclic (비순환)**: `T1 → T2 → T1` 같은 순환 금지. 그래야 "언젠가 반드시 끝난다"가 보장됨.
- **Graph**: 노드(Task) + 엣지(의존성).

```
P1 (선형):   T1 ──→ T2 ──→ T3

분기 예시:           ┌──→ T3 ─┐
            T1 → T2 ┤        ├──→
                     └──→ T4 ─┘
```

**그래프를 쓰는 이유**: 오케스트레이터는 이 그래프만으로 "지금 실행 가능한 Task"를 기계적으로 계산한다.
**핵심 규칙**: **상류(upstream) Task가 전부 성공하면, 그 Task는 실행 가능하다.**

### 의존성과 실패 전파 (→ 시나리오 C)

P1이 실패하면 P2의 상류 조건("P1 전체 성공")이 깨져 **P2는 트리거되지 않고 blocked 상태로 명시**된다.

- cron은 **시간**만 보고 P2를 실행 → P1 실패 시에도 돌아 **조용히 틀린 결과** 생성 (운영상 가장 위험).
- 오케스트레이터는 **상류 결과**를 보고 P2를 깨움 → 잘못된 실행 자체를 차단.

이것이 과제 **시나리오 C**(P1 T3 실패 → P2·P3 차단)의 원리.

## 1.3 Scheduler / Executor / Worker / MetaDB

DAG는 "무엇을 어떤 순서로"를 **표현**할 뿐. 실제 실행은 역할이 분리된 컴포넌트들이 담당한다.

| 컴포넌트 | 역할 | 한 줄 |
|---|---|---|
| **Scheduler** | 판단·선별 | DAG+시계 보고 실행 가능 Task 조회 → **우선순위 정렬 + 슬롯 한도 확인** → 선택된 것만 넘김 |
| **Executor** | 실행 방식 | 넘겨받은 Task를 워커에 배치. 종류(Local/Celery/Kubernetes)가 워커 위치·확장성을 결정 (→ [심화 A](#sim-a)) |
| **Worker** | 실행 | 실제 코드(Spark Job)를 돌리는 프로세스 |
| **MetaDB** | 공유 상태 | 모든 Task 상태·이력·스케줄의 single source of truth. 컴포넌트 간 소통 + 가시성(④)의 원천 |

### 실행 흐름 루프 (P1)

```
정각 → Scheduler: "T1은 상류 없음 → 실행 가능" → (우선순위·슬롯 한도 확인) → Executor로
     → Executor: 워커에 배정
     → Worker: SparkSession 생성 → stub 실행 → "성공"을 MetaDB에 기록
     → Scheduler: MetaDB 읽고 "이제 T2 차례" → 반복
```

**역할 분리의 이유 = 독립 확장.** 작업이 밀리면 **워커만 늘리면** 됨(판단 로직 불변). 1대든 100대든 "판단"은 동일하고 "실행"만 스케일한다.

> Scheduler와 Executor의 역할 구분, Executor 종류별 동작 → [심화 A](#sim-a)

## 1.4 우선순위 / 동시성

### 우선순위 — Scheduler가 처리 (FIFO vs 우선순위 큐)

큐를 단순 FIFO(먼저 온 것 먼저)로 보기 쉽지만, 우선순위가 있으면 **우선순위 큐**가 된다.

```
실행 가능: P3-T1(우선순위 3), P1-T1(2), P4-T3(0)    남은 슬롯 1개
→ Scheduler가 우선순위 정렬 → 슬롯을 P3(3)에 먼저 → P4(0)는 대기
→ 슬롯 반납 시 다시 우선순위 순으로 선택
```

- Airflow `priority_weight`, Dagster `priority` = 이 정렬에 쓰는 **속성값**. 사용 주체는 **Scheduler**.
- `didimdp_manager` 한계 ①과 직결: "대기열 FIFO 고정 → 긴급 작업이 먼저 실행 안 됨". **시나리오 A**가 검증하는 차이.
- ⚠️ 우선순위는 *대기 중인 것 중 선택*에만 작동. **실행 중 Task는 중단하지 않는다** → [심화 B](#sim-b)

### 동시성 — 슬롯은 "논리 카운터"

오케스트레이터의 슬롯/Pool/동시성 한도는 **논리적 카운터**일 뿐, 실제 CPU·메모리를 측정하지 않는다.

- `슬롯=3` = "동시에 슬롯 쥔 Task 3개까지". 각 Task가 CPU를 얼마 쓰든 오케스트레이터는 모름(+1/−1만).
- `didimdp_manager` 한계 ②와 직결: "**로컬 카운터** 기반 → **실제 Spark 자원과 괴리**". 카운터는 "여유 있음"이라는데 기계는 메모리가 터지는 상황.
- **우리 과제**: Spark `local[*]` 단일 JVM → 진짜 자원 관리자 없음. "슬롯 3개"는 순수 Pool 카운터로만 강제(자원 경합의 논리적 시뮬레이션). **시나리오 B**의 무대.
- 그럼 실제 물리 자원은 누가? → [심화 C](#sim-c) / 두 계층 비교 → [심화 D](#sim-d)

## 1.5 스케줄 트리거

DAG Run을 시작시키는 방아쇠는 세 종류.

| 트리거 유형 | 설명 | 과제 매핑 |
|---|---|---|
| **시간 기반 (cron)** | cron 표현식으로 실행 시점 지정 | P1 `0 * * * *`(매시간), P3 `0 0 * * *`(자정), P4 `0 2 * * 1`(월 02:00) |
| **수동/외부 (API·UI)** | 사람·외부 시스템이 직접 트리거 | P3 긴급 정산 (관리자 수동 API) |
| **이벤트/센서** | 다른 작업 완료·파일 도착 등 조건 충족 시 반응 | P2가 P1 완료를 기다렸다 시작 |

- cron 표현식 = `분 시 일 월 요일`. 예: `0 2 * * 1` = 매주 월요일 02:00.
- P3는 **두 트리거 동시 보유**: 평소 cron(자정) + 급할 때 수동 API. 시나리오 A의 "긴급 트리거"가 이 수동 경로.

## 1.6 Retry — 일시적 실패 흡수

Task 실패 시 정해진 횟수만큼 **자동 재시도**. 실패는 두 종류로 갈린다.

- **일시적(transient)**: 네트워크 끊김, DB 일시 락, 자원 부족 — 다시 하면 성공 가능 → Retry로 흡수
- **영구적(permanent)**: 코드 버그, 잘못된 입력 — 재시도해도 실패 → 횟수 소진 후 최종 실패

| 설정 요소 | 의미 |
|---|---|
| `retries` | 최대 재시도 횟수 |
| `retry_delay` | 실패 후 재시도까지 간격 |
| 지수 백오프 | 재시도할수록 간격 증가(1→2→4분), 장애 회복 시간 확보 |

과제 연결: P1의 T1·T3, P2의 T4는 실패율 설정 stub. Retry로 일시적 실패는 자동 통과, 진짜 문제일 때만 최종 실패해 의존 파이프라인을 차단(시나리오 C).

## 1.7 멱등성(Idempotency) — 재실행의 안전 전제

**정의**: 같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 동일한 성질.

Retry든 선택적 재실행이든 결국 **이미 한 번 (부분) 실행된 Task를 다시 도는 일**이라, 멱등하지 않으면 재실행이 데이터를 망가뜨린다.

```
멱등하지 않은 T3(append):  첫 시도가 절반 적재 후 실패 → 재실행 시
   → PK 제약 있으면 중복 키 에러, 없으면 조용히 중복 저장 ❌

멱등한 T3(overwrite/upsert):  해당 시간대 파티션 통째 덮어쓰기
   → 몇 번 재실행해도 결과는 "그 시간대 데이터 1벌" ✅
```

- 멱등성 패턴: **파티션 overwrite**, **DELETE + INSERT**, **MERGE/upsert**, **트랜잭션**
- 시나리오 C의 전제: "T3만 재실행 → 성공 시 P2·P3 재개"가 안전하려면 T3가 멱등해야 중복 없이 다시 돈다.

**Retry vs 선택적 재실행** (둘 다 재실행, 목적이 다름)

| | Retry | 선택적 재실행 |
|---|---|---|
| 대상 실패 | 일시적 | 영구적(원인 수정 후) |
| 시점 | 실패 직후 자동, 같은 Run 내 | 나중에 사람이 수동 |
| 성격 | 자동 흡수 장치 | 운영 복구 행위 (시나리오 C) |
| 공통 전제 | 멱등성 | 멱등성 |

---

## 1.8 Backfill — 놓친 과거 구간 소급 실행

각 스케줄 실행은 **시간 구간(data interval)** 에 대응한다 (P1 14:00 Run = 13~14시 주문 처리). 그래서 과거 구간을 지목해 실행할 수 있다.

**Backfill** = 실행 안 됐거나 다시 돌려야 하는 과거 구간들을 소급해 채우는 것.

```
P1이 장애로 02:00~05:00(3개 정각) 멈춤 → 복구 후
backfill로 02:00·03:00·04:00 Run 소급 실행해 누락 메움
```

- **멱등성 전제**: 이미 일부 돈 구간을 다시 돌려도 안전해야 함
- 과거 구간을 한꺼번에 돌리면 **자원 경합**(슬롯 부족) 발생 → 동시성 제어와 함께 봐야 함

<a id="sim-a"></a>
## 심화 A — Scheduler와 Executor의 역할 구분 / Executor 종류
> 본문 [1.3](#13-scheduler--executor--worker--metadb) 보충

Executor는 Scheduler가 호출하는 컴포넌트로, 넘겨받은 Task를 워커에 배치해 실행한다. 실행 *방식*을 정하는 것은 **어떤 Executor를 쓰느냐(종류 선택)** 다.

종류별로 실제 하는 일:

| Executor 종류 | 주체로서 하는 일 | Worker 위치 |
|---|---|---|
| **LocalExecutor** | 스케줄러와 **같은 기계에서 서브프로세스**를 띄워 실행 | 같은 기계 |
| **CeleryExecutor** | Task를 **메시지 브로커(Redis 등)에 던짐** → 별도 워커가 가져가 실행 | 다른 서버(들) |
| **KubernetesExecutor** | Task마다 **새 파드(pod)를 생성**해 실행 | 파드 |

동작을 풀어보면:
- Scheduler가 선택한 Task를 **Executor에 건넨다**.
- Executor가 **자기 종류의 방식대로** 그 Task를 워커(서브프로세스/Celery 워커/파드)에 배치한다.

**경계 정리**:
```
Scheduler = 무엇을 / 얼마나 / 어떤 순서로 보낼지 판단 (우선순위·슬롯 한도)
Executor  = 받은 걸 "어디서 어떻게" 굴릴지 수행하는 실제 컴포넌트
Worker    = Executor가 띄운, 코드가 실제 도는 프로세스
```
LocalExecutor는 Executor·Worker가 같은 기계라 붙어 보이고, Celery·Kubernetes는 Worker가 분리돼 **확장성**이 드러난다.

<a id="sim-b"></a>
## 심화 B — 실행 중 Task와 우선순위 (no-preemption)
> 본문 [1.4](#14-우선순위--동시성) 보충

**규칙: 이미 실행 중인 Task는 우선순위 때문에 중단되지 않는다 (no preemption).** 우선순위는 오직 *대기 중인 것들 중 다음에 시작할 것*을 고를 때만 작동한다.

예: `Pa(Ta-Tb-Tc)`, `Pb(Ta-Tb-Tc)`, Pb 우선순위↑, `Pa.Tb` 실행 중 `Pb.Ta` 트리거 시
- ❌ `Pa.Tb`를 죽이고 `Pb.Ta` 실행 → **아니다**.
- ✅ `Pa.Tb`는 **끝까지 완료**. 그 후 슬롯이 비고, 자원이 부족해 `Pa.Tc`와 `Pb.Ta`가 경합하면 → **우선순위 높은 `Pb.Ta`가 먼저** 슬롯 확보.
- 자원 여유가 있으면 → 둘 다 시작(경합 없음).

**과제에서 "선점"의 의미**: 시나리오 A의 "우선순위 선점"은 *실행 중 Task를 죽이는 것*이 아니라 **새로 비는 슬롯을 우선순위 높은 쪽이 먼저 가져가는 것**.
> P4 T3(슬롯 2)는 계속 돌고, P3는 남은 슬롯 1로 즉시 시작 → 이후 추가 슬롯을 P3가 먼저 확보하는지가 검증 포인트.

(참고: 진짜 실행 중 강제 종료 preemption은 YARN 같은 *자원 관리자* 레벨엔 존재. Airflow/Dagster *Task 레벨*에선 일반적으로 안 함.)

<a id="sim-c"></a>
## 심화 C — 실무에서 물리 CPU/메모리는 누가 관리하나
> 본문 [1.4](#14-우선순위--동시성) 보충

> **오케스트레이터는 Spark의 물리 자원을 관리하지 않는다. "Job 제출"만 한다. 실제 CPU·메모리 할당은 *Spark의 클러스터 매니저*가 한다.**

실무 흐름:
```
① Airflow Scheduler: "정각·슬롯 있음 → 이 Spark Job 제출" (논리 스케줄링·동시성)
② Airflow Executor → SparkSubmitOperator가 'spark-submit' 실행
        (spark-submit '클라이언트 프로세스'가 도는 위치 = Airflow Executor가 결정)
③ spark-submit이 Spark 클러스터 매니저에 제출
        → YARN/K8s가 실제 코어·메모리 보고 Spark executor 할당   ← 물리 자원의 주체
④ Spark executor들이 분산 처리 수행
```

물리 자원 관리 도구 후보:

| 환경 | 클러스터 매니저 / 도구 |
|---|---|
| 전통적 하둡 스택 | **YARN** (가장 흔함) |
| 컨테이너 기반 | **Spark on Kubernetes** |
| 단순/소규모 | **Spark Standalone** |
| 매니지드 | **AWS EMR, Databricks, GCP Dataproc** |

Airflow는 `--num-executors`, `--executor-memory`, `--executor-cores` 같은 **요청값만** 실어 보내고, 실제 할당은 YARN/K8s가 한다.

**유의**: 물리 배치는 "Airflow 워커"가 아니라 **Spark가 제출될 때 Spark 자신의 클러스터 매니저(YARN)** 가 한다. **Airflow 워커**(spark-submit을 누르는 손) ≠ **Spark executor**(실제 분산 연산 단위). 우리 과제는 `local[*]`로 이 단계를 통째로 접어 클러스터 매니저가 없다.

<a id="sim-d"></a>
## 심화 D — 오케스트레이터 vs 자원 관리 매니저 비교
> 본문 [1.4](#14-우선순위--동시성) 보충

둘은 경쟁이 아니라 **위아래로 협력하는 두 계층**이다.

| 구분 | 오케스트레이터 (Airflow/Dagster) | 자원 관리 매니저 (YARN/K8s/매니지드) |
|---|---|---|
| 핵심 질문 | **무엇을 / 언제 / 어떤 순서로** 실행할까 | 이 작업을 **어느 노드에 / 코어·메모리 얼마**로 띄울까 |
| 다루는 단위 | DAG·Task·Run, 의존성, 스케줄 | 컨테이너/컨테이너 그룹, 코어, 메모리 |
| "동시성" 의미 | **논리 슬롯 카운터** (실제 자원과 분리) | **실제 물리 자원** 가용량 |
| 우선순위 | 대기 Task 선택 순서 (no-preempt) | 실제 자원 선점 가능(예: YARN preemption) |
| 관점 | "파이프라인이 제대로 돌았는가" | "클러스터 자원이 효율적으로 쓰이는가" |
| 실패 시 | 재시도·의존성 차단·알림 | 컨테이너 재배치·자원 회수 |
| 우리 과제 | Airflow/Dagster가 담당 | **없음** (`local[*]`로 생략, 슬롯은 논리 시뮬레이션) |

**협력 관계 한 줄**: 오케스트레이터가 "이 Job을 지금 돌려라"고 **결정·제출**하면, 자원 매니저가 "그럼 이 노드에 이만큼 줘서 띄우겠다"고 **물리 배치**한다. 오케스트레이터의 논리 슬롯과 자원 매니저의 실제 자원이 **어긋날 수 있다는 점**이 `didimdp_manager` 한계 ②의 본질이다.
