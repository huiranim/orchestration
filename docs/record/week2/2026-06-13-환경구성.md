## 1. 버전 선택 근거

| 항목 | 선택 | 근거 |
|---|---|---|
| apache-airflow | 2.10.4 | 최신 2.x stable. Airflow 3.x는 출시 초기라 레퍼런스 부족. 2.10.x가 가장 성숙한 버전 |
| constraints 파일 | 공식 제공 (constraints-2.10.4/constraints-3.11.txt) | Airflow는 의존성 충돌이 잦아 공식 constraints 없이 설치하면 resolver 실패 가능 |
| Python (constraints 기준) | 3.11 | constraints 파일이 3.11 기준 제공. 3.12+ 는 Airflow 2.10 기준 일부 패키지 미지원 |
| Java | 21 (Homebrew, 이미 설치된 버전) | PySpark는 Java 11+ 지원. 21 LTS도 문제없음 |
| Executor (Airflow) | SequentialExecutor | airflow standalone 기본값. P1 순차 파이프라인에는 충분. LocalExecutor는 Postgres 필요 |
| DB (Airflow) | SQLite | airflow standalone 기본값. 컨테이너 없이 즉시 사용 가능 |

## 2. 전제 조건 확인

### Java
```bash
java -version
# openjdk version "21.0.10" 2026-01-20 (Homebrew)
```

JAVA_HOME 미설정 상태 확인 → 수동 설정 필요.

**이슈**: `/usr/libexec/java_home -v 21` 실패 — Homebrew Java는 macOS 기본 탐색기에 자동 등록되지 않음.  
**해결**: Homebrew 경로 직접 지정.

```bash
export JAVA_HOME=$(brew --prefix openjdk@21)
echo 'export JAVA_HOME=$(brew --prefix openjdk@21)' >> ~/.zshrc
```

**주의**: `brew --prefix openjdk`는 최신 버전(25)을 가리킴. 반드시 `openjdk@21`로 명시.

### Python
```bash
# macOS에서 python 명령어 없음 → python3 사용
python3 --version
```

## 3. Airflow 환경 구성

### venv 생성
```bash
cd orchestration/airflow/
python3 -m venv .venv && source .venv/bin/activate
# (.venv) 프롬프트 확인
```

### 패키지 설치
```bash
pip install apache-airflow==2.10.4 pyspark pytest \
  --constraint "https://raw.githubusercontent.com/apache/airflow/constraints-2.10.4/constraints-3.11.txt"
```

### 환경변수 영속화
`.venv/bin/activate` 하단에 다음 export 추가 (venv 활성화 시마다 자동 적용):
```bash
export AIRFLOW_HOME="$(dirname "$VIRTUAL_ENV")/.airflow"
export AIRFLOW__CORE__DAGS_FOLDER="$(dirname "$VIRTUAL_ENV")/dags"
export AIRFLOW__SCHEDULER__DAG_DIR_LIST_INTERVAL=10
export PYTHONPATH="$(dirname "$VIRTUAL_ENV")/macos_shims:$PYTHONPATH"  # 아래 SIGSEGV 이슈 참고
export AIRFLOW__CORE__LOAD_EXAMPLES=False  # 예제 DAG 69개 미로드 (적용 후 airflow db reset 필요)
```

### 이슈: macOS gunicorn 워커 SIGSEGV (중요)

**증상**: `airflow standalone` 실행 시 webserver/triggerer 워커가 `Worker (pid:...) was sent SIGSEGV!`를 초당 수백 건 출력하며 무한 재시작. UI 접속 불가.

**디버깅 과정**:
1. 스케줄러는 멀쩡하고 gunicorn 기반 컴포넌트(webserver, triggerer)만 죽음 → fork 관련 의심
2. macOS 크래시 리포트(`~/Library/Logs/DiagnosticReports/Python-*.ips`)의 faulting thread 스택 분석:
   ```
   libsystem_trace.dylib   _os_log_preferences_refresh   ← 크래시 지점
   CoreFoundation          _CFBundleLoadExecutableAndReturnError
   _setproctitle...so      darwin_set_process_title
   ```

**근본 원인**: gunicorn이 워커를 `fork()`한 뒤 각 워커가 `setproctitle` C 확장으로 프로세스명을 변경. 이 라이브러리의 darwin 구현이 fork 직후 CoreFoundation을 호출하는데, CoreFoundation은 fork-safe하지 않아 SIGSEGV 발생. (`OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES`는 ObjC 런타임의 fork *abort*만 억제하므로 이 하드 segfault에는 무효)

**해결**: `setproctitle`은 `ps` 출력상 프로세스명 표시용 cosmetic 기능이라 오케스트레이션 동작에 영향 없음. 동일 이름의 no-op 모듈(`airflow/macos_shims/setproctitle.py`)을 만들어 `PYTHONPATH`로 site-packages보다 앞에 두어 C 확장을 shadow. 모든 import 구문은 그대로 동작.

**한계/주의**: 정석 해결책은 아님(macOS 전용 우회). 표준 대안은 Docker Compose로 Airflow를 Linux 컨테이너에서 실행하는 것. 이 과제는 학습 목적이라 셰임으로 standalone을 유지하기로 결정.

**검증**: 셰임 적용 후 `curl http://localhost:8080/health` → HTTP 200, SIGSEGV 0건. webserver/scheduler/triggerer/gunicorn(워커 4개) 모두 정상.

### UI 접속 확인
`http://localhost:8080` 접속 → admin 로그인. 임시 패스워드는 `.airflow/standalone_admin_password.txt`에 저장됨.

## 4. Dagster 환경 구성

> 실행일: 2026-06-13. dagster 1.13.9 (Python 3.11)

### venv 생성 및 패키지 설치
```bash
cd orchestration/dagster/
/opt/homebrew/opt/python@3.11/bin/python3.11 -m venv .venv && source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt   # dagster, dagster-webserver, pyspark
```

requirements.txt:
```
dagster
dagster-webserver
pyspark
```

**이슈: 첫 venv가 Python 3.9로 생성됨**
- `python3`이 시스템 기본(3.9.6)을 가리켜 `cp39` 휠로 설치됨. Airflow(3.11)와 버전 불일치 + 구버전 pip(21.2.4) 경고.
- Airflow에서 Python 3.9 LibreSSL 문제를 겪었던 터라, 일관성·예방 차원에서 **3.11로 재생성**.
- 해결: venv 삭제 후 `python@3.11` 경로를 명시해 재생성 (위 명령). 이후 `cp311` 휠 + pyspark wheel 빌드 정상.

### 실행 방법 (Airflow standalone과 차이)
```bash
dagster dev -f definitions.py
```

**이슈: `dagster dev` 인자 없이는 실패**
- `dagster dev`만 실행하면 `No arguments given and no [tool.dagster] block in pyproject.toml found` 에러.
- Dagster는 진입점(파일/모듈)을 명시해야 함. `-f definitions.py`로 지정해 해결.
- (Airflow는 `DAGS_FOLDER`로 폴더를 자동 스캔하는 방식과 대비됨)

**경고: `dagster dev` deprecated**
- `Function dev_command is superseded... Use 'dg dev' instead` 경고 출력. 동작엔 지장 없어 `dagster dev` 유지.

### 환경변수 영속화 (DAGSTER_HOME)
우선순위/동시성 실험을 위해 `dagster.yaml`을 읽도록 `DAGSTER_HOME`을 고정.
`.venv/bin/activate` 하단에 추가:
```bash
export DAGSTER_HOME="$(dirname "$VIRTUAL_ENV")/.dagster_home"
```
- 설정 전: `dagster dev`가 임시 폴더를 써서 매 실행마다 설정·이력이 사라짐("Using temporary directory..." 경고).
- 설정 후: `.dagster_home/dagster.yaml`을 읽고 실행 이력도 보존됨.

### dagster.yaml (동시성 풀 + deadlock 방지)
`.dagster_home/dagster.yaml`:
```yaml
concurrency:
  pools:
    default_limit: 1          # op 풀 슬롯 기본 제한 1 (우선순위 실험용)
run_monitoring:
  enabled: true
  free_slots_after_run_end_seconds: 60   # 풀 슬롯 deadlock 방지(공식 문서 권장)
```
- **deadlock 주의**: 풀 사용 시 run 취소/실패하면 슬롯이 자동 반환되지 않음. `default_limit:1`에서 영구 deadlock 가능 → `run_monitoring`으로 종료 후 자동 반환.

### UI 접속 확인
`http://localhost:3000` 접속. 인증 없음(로컬 dev). Assets는 **Lineage** 탭, Jobs는 **Jobs** 탭에서 확인.

## 5. 셋업 체감 비교 (Airflow vs Dagster)

| 항목 | Airflow | Dagster |
|---|---|---|
| Python 버전 | 3.11 (3.9는 LibreSSL 문제로 불가) | 3.11 (3.9도 설치는 되나 일관성 위해 통일) |
| 의존성 설치 | constraints 파일 필수, 무거움 | `pip install -r` 한 줄, 가벼움 |
| 핵심 명령어 | `airflow standalone` | `dagster dev -f definitions.py` |
| 진입점 지정 | `DAGS_FOLDER` 폴더 자동 스캔 | 파일/모듈 명시(`-f`) 또는 `pyproject.toml` |
| 주요 막힌 지점 | macOS SIGSEGV(셰임 필요), Python 3.9, 예제 DAG, 스캔 지연 | Python 3.9 재생성, `-f` 필요, DAGSTER_HOME 설정 |
| 동시성 설정 | `airflow pools set` CLI 한 줄 | `dagster.yaml` 인스턴스 설정 |
| macOS 고유 문제 | 있음(gunicorn fork) | 없음(uvicorn 단일 프로세스) |

> 종합: 셋업 자체는 Dagster가 가벼웠으나, 양쪽 다 Python 3.11 통일이 필요했다. 상세 기능 비교 및 도구 선택은 [[05-비교분석]] 참고.
